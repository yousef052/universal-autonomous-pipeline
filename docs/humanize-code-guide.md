# دليل صياغة الكود البشري الخبير (Humanize Code Craftsmanship Guide)

> **كيف تصيغ كوداً يماثل فكر وخبرة مهندسي البرمجيات المخضرمين (Staff/Principal Engineers) ويقضي على بصمات الذكاء الاصطناعي الروبوتية.**

---

## 💡 الفلسفة الهندسية: لماذا نحتاج لسكيل Humanize؟

الذكاء الاصطناعي العام يمتلك عادة عادات إحصائية متكررة تجعل الكود يبدو "مصنوعاً آلياً":
- **التعليقات الببغائية (Parrot Comments):** كتابة تعليقات تشرح البديهيات مثل `// Loop through items` أو `// Return result`.
- **الأسماء العامة الميتة:** استخدام كلمات خالية من المعنى مثل `data`, `res`, `item`, `temp`, `handleProcess()`.
- **الهندسة الزائدة المبكرة (Overengineering):** إنشاء 4 واجهات وFactory لدالة بسيطة تُستدعى في مكان واحد.
- **تدرج الأهرامات (Arrowhead Anti-pattern):** تداخل الشروط 5 مستويات للداخل (`if { if { if { ... } } }`).
- **رسائل أخطاء روبوتية غامضة:** رمي أخطاء مثل `throw new Error("Invalid input")` دون ذكر القيمة أو المعرف.

سكيل **`humanize-code`** يُعيد ضبط جودة الكود البرمجي ليعكس حكمة وبراغماتية المهندس البشري الخبير.

---

## 🏛️ الركائز الـ 7 لصياغة الكود البشري الخبير

```
┌────────────────────────────────────────────────────────────────────────┐
│                   HUMAN CODE CRAFTSMANSHIP                             │
├────────────────────────────────────────────────────────────────────────┤
│ 1. تطهير بصمات الآلة    │ حذف التعليقات التافهة والأسماء الروبوتية      │
│ 2. قانون "لماذا لا ماذا" │ التعليق مخصص فقط لأسباب البيزنس أو الثغرات    │
│ 3. سردية لغة النطاق      │ الأسماء تمثل واقع النظام المالي والتشغيلي     │
│ 4. حراس الخروج المبكر   │ استخدام Guard Clauses وتسطيح هامش الكود       │
│ 5. الفصاحة اللغوية      │ استخدام أحدث ميزات اللغة المريحة (Ergonomics) │
│ 6. التعاطف التشغيلي     │ رسائل أخطاء تفصيلية تنقذ مهندس المناوبة ليلاً  │
│ 7. الإيقاع البصري       │ تقسيم الكود لفقرات منطقية ذات تنفس مريح       │
└────────────────────────────────────────────────────────────────────────┘
```

---

### 1. تطهير بصمات الآلة (Anti-AI Smells)
- **احذف التعليقات التي تكرر الكود:** إذا كان السطر التالي يقول `if (!user) return null;`، فلا تكتب قبله `// Check if user is null`.
- **احذف المتغيرات المؤقتة الزائدة:** تجنب `const result = compute(); return result;`، بل اكتب مباشرة `return compute();`.
- **احظر الكلمات المحرمة:** `data`, `item`, `res`, `temp`, `val`, `manager`, `helper`.
- **حارب التعقيد المسبق:** لا تنشئ Interface إلا إذا كان هناك تعدد حقيقي في التطبيقات (Polymorphism) أو حاجة لعزل تبعية خارجية في الاختبارات.

---

### 2. قانون التعليقات عالي الإشارة (The "WHY, Not WHAT" Law)
المهندس المحترف يكتب التعليق فقط عندما يعجز الكود الصريح عن شرح **سبب** اتخاذ قرار غريب:
- أسباب تتعلق بقواعد بيزنس مفاجئة.
- حلول ترقيعية لعيوب ومشاكل في مكتبات خارجية (Vendor Workarounds).
- تبرير مقايضات الأداء الواعية (Performance Trade-offs).

```typescript
// NOTE: بوابة الدفع تُرجع null بدلاً من 0 في الفواتير المجانية.
const feeAmount = invoice.fee ?? 0;

// HACK: متصفح سفاري يتجاهل overflow: hidden مع الرسوم المتحركة ثلاثية الأبعاد.
const modalStyles = "isolation-auto overflow-hidden";
```

---

### 3. سردية لغة النطاق والأسماء المعبرة (Domain Storytelling)
- **المتغيرات المنطقية (Booleans):** يجب أن تُقرأ كسؤال نحوي إجابته نعم/لا (`isAvailable`, `hasGracePeriodExpired`, `canRefundTransaction`).
- **المجموعات (Collections):** استخدم أسماء جمع تدل على الكيان (`pendingInvoices`, `settledLedgerEntries`).
- **الأفعال (Verbs):** استخدم أفعالاً دقيقة (`reconcile`, `revoke`, `disburse`, `supersede`).

---

### 4. حراس الخروج المبكر (Flat Guard Clauses)
- تخلص من شكل الهرم المتداخل عبر فحص الشروط السلبية أولاً والخروج المبكر (`return early` أو `throw`).
- مسار النجاح الأساسي (Happy Path) يجب أن يظل مستقيماً ومحاذياً للهامش الأيسر بدون إزاحات داخلية لا نهائية.

---

### 5. الفصاحة اللغوية الحديثة (Idiomatic Fluency)
- في **C# 12 / .NET 8:** استخدم Primary Constructors، و Collection Expressions `["a", "b"]`، و Pattern Matching `user is { Address: not null }`.
- في **TypeScript:** استخدم Discriminated Unions لتمثيل حالات الواجهة بدلاً من مجموعة booleans متضاربة، والـ Type Predicates للتحقق الآمن.
- في **Python:** استخدم List Comprehensions ومكتبة Dataclasses ومديري السياق `with`.

---

### 6. التعاطف التشغيلي ورسائل الأخطاء (Operational Empathy)
عندما يحدث خطأ في السيرفر في منتصف الليل، يجب أن تحتوي رسالة الاستثناء في الـ Log على:
- ما الذي حدث بالضبط؟
- ما هي القيمة الخاطئة الممررة؟
- ما هو المعرف (ID) للكيان المتأثر؟
- ما هي القيم المقبولة؟

```typescript
// ✅ رسالة خطأ إنسانية تسعف مهندس الصيانة:
throw new InvalidTransferException(
  `Transfer amount must be positive. Received '${amount}' for account '${accountId}'.`
);
```

---

### 7. الإيقاع البصري وتنظيم الفقرات (Visual Rhythm)
نسّق الكود كما تُنسق مقالاً أدبياً:
1. **فقرة المدخلات وحراس الفحص (Guard Clauses)**
2. *[سطر فارغ]*
3. **فقرة الحسابات والمنطق الأساسي**
4. *[سطر فارغ]*
5. **فقرة الحفظ والتأثيرات الجانبية (Persistence / Side Effects)**
6. *[سطر فارغ]*
7. **سطر الإرجاع النهائي**

---

## 📋 قائمة المراجعة السريعة (10-Point Audit Checklist)

قبل اعتماد أي كود برمجي، راجع هذه النقاط العشر:

1. [ ] **صفر تعليقات ببغائية:** هل تم حذف كل تعليق يكرر ما يقوله الكود؟
2. [ ] **التعليق لـ "لماذا" فقط:** هل التعليقات المتبقية تشرح أسباب بيزنس أو قيود أداء فقط؟
3. [ ] **غياب الأسماء الروبوتية:** هل استبدلت كلمات `data` و `temp` و `item` بأسماء من واقع النطاق؟
4. [ ] **هامش أيسر مسطح:** هل اعتمدت على Guard Clauses وتجنبت الأهرامات المتداخلة؟
5. [ ] **إرجاع مباشر:** هل حذفت المتغيرات الوسيطة المؤقتة التي تسبق أمر `return` مباشرة؟
6. [ ] **أخطاء إنسانية واضحة:** هل توضح رسائل الاستثناءات القيمة الممرضة والمعرف وسبب الرفض؟
7. [ ] **صيغ لغوية حديثة:** هل يستغل الكود أحدث قدرات لغة البرمجة بدلاً من الأنماط الموروثة القديمة؟
8. [ ] **غياب التجريدات الزائفة:** هل بسطت الواجهات والمصانع التي لا داعي لوجودها؟
9. [ ] **تنظيم الفقرات والتنفس البصري:** هل توجد أسطر فارغة تفصل بين مراحل المعالجة بوضوح؟
10. [ ] **الوعي بحالات الحواف (Idempotency):** هل يتعامل الكود بأناقة مع العمليات المكررة أو المتطابقة؟
